# Роли, группы, доступ к задачам и журнал активности

## TL DR

Предлагается единая модель безопасности AgileTracker: глобальные роли `admin`, `manager`, `user` через Spatie permissions ограничивают возможные действия, а типизированные группы и участники Item — видимость и права конкретной записи. Для row-level доступа сохраняются два варианта: **Jira-like** security schemes либо рекомендуемый **Planfix-like** с участниками, группами и руководителями; итоговое право всегда является пересечением глобальной роли и доступа к Item. Существующий Sanctum остаётся API-аутентификацией, а `relaticle/activity-log` и read-only раздел `/settings/activity-log` дают историю записи и общий административный аудит.

## Контекст

**Situation.** В `ItemPolicy` методы `view`, `create`, `update` и `delete` разрешены всем аутентифицированным пользователям. Спецификация [REST API v1](../../specs/rest-api.md) подтверждает, что Item не имеет perimeter-фильтра, а [Boards](../../specs/boards.md) прямо фиксирует плоский доступ. При этом у Item уже есть постановщик (`reporter_id`), исполнитель (`assignee_id`), адресаты (`item_to`) и наблюдатели (`item_cc`), а роли Spatie `admin`, `manager`, `user` пока не образуют предметную модель прав на задачи. Панель `/settings` уже admin-only, API использует Sanctum token abilities, но разрешения Spatie не созданы. `spatie/laravel-activitylog` установлен, однако `LogsActivity` подключён только к Item, что противоречит утверждению `AGENTS.md` о логировании каждой модели.

**Complication.** Без глобальной матрицы роли `manager` и `user` почти неразличимы, а без групп и row-level visibility нельзя разделить проекты, команды и подразделения: скрытие записи только в Filament-таблице оставит её в API, на досках, в комментариях, виджетах и по прямой ссылке. Для Jira характерны permission schemes и независимые issue security schemes; для Planfix — доступ к каждой задаче по её участникам, группам, аудиторам и руководителям. В Redmine доступ задаётся не у задачи, а у проекта. Одновременно администратору нужен безопасный способ расследовать изменения без записи паролей, токенов и технических перемещений в журнал.

**Question.** Как совместить глобальные роли, группы типов `project`, `team`, `department` и других, ограничение конкретных задач и аудит без рассинхронизации Filament, REST и смежных сущностей?

**Answer.** Ввести каталог разрешений и общую модель групп, затем применять единый `ItemAccess` как дополнительный perimeter поверх глобальных permissions. Два варианта row-level доступа описаны ниже как ветки одного RFC; в delivery реализуется только выбранная ветка, базовая рекомендация — Planfix-like. Sanctum и policies остаются независимыми барьерами API, Passport без требований OAuth2 не добавляется. Единое хранилище Spatie activity log обслуживает и timeline Item, и общий журнал администратора.

## Назначение и цели

- Разграничить возможности `admin`, `manager`, `user` одинаково в Filament, Livewire-действиях и REST API v1; дать администратору безопасное назначение одной роли без потери последнего администратора.
- Дать администратору управляемые группы пользователей с типами и составом, пригодные для проектов, команд и подразделений.
- Ограничить видимость конкретной задачи группами и участниками, не позволяя access grant расширять действие сверх глобальной роли.
- Централизовать авторизацию так, чтобы список, карточка, связи, доски, комментарии, дашборд, поиск и REST API возвращали согласованный результат.
- Не скрывать исторические задачи до явной настройки ограничений и не смешивать доступ с workflow status, labels и board membership.
- Сохранить текущие token abilities и Sanctum, зафиксировав два варианта row-level доступа до реализации.
- Покрыть аудитом доменные и административные изменения, дать пользователю timeline Item, а администратору — общий read-only журнал с маскировкой секретов.

Заинтересованные стороны: администраторы, менеджеры, руководители групп, постановщики и исполнители задачи, обычные пользователи, клиенты REST API v1, maintainers и ревьюеры безопасности. Ревью требуется продуктовое (выбор Jira/Planfix-модели), архитектурное и по безопасности (пересечение глобальных и row-level прав, полнота perimeter-фильтров, redaction аудита).

## Составляющие и особенности

### 1. Глобальные роли, разрешения и их назначение

Ввести string-backed enums для имён ролей и разрешений. Роли остаются `admin`, `manager`, `user`; каталог permissions группируется по сущностям: `items.view`, `items.create`, `items.update.related`, `items.update.all`, `items.delete`, `labels.view`, `labels.manage`, `boards.view`, `boards.manage`, `comments.view`, `comments.create`, `comments.moderate`, `users.view`, `users.manage`, `groups.manage`, `settings.manage`, `activity.view`.

| Возможность | admin | manager | user |
|---|---|---|---|
| Просматривать доступные Items, Labels, Boards, Comments и профили Users | Да | Да | Да |
| Создавать Items и Comments | Да | Да | Да |
| Изменять доступный Item, где пользователь reporter или assignee | Да | Да | Да |
| Изменять любой доступный Item | Да | Да | Нет |
| Удалять доступные Items | Да | Да | Нет |
| Управлять Labels и структурой Boards | Да | Да | Нет |
| Изменять, удалять и закреплять собственные Comments | Да | Да | Да |
| Модерировать чужие Comments | Да | Да | Нет |
| Управлять Users, их ролями и Groups | Да | Нет | Нет |
| Изменять General settings | Да | Нет | Нет |
| Просматривать общий Activity log | Да | Нет | Нет |

«Свой Item» для `items.update.related` означает только `reporter_id = current user` или `assignee_id = current user`; наличие пользователя в `to`/`cc` само по себе глобального права изменения не даёт. Матрица — верхний предел возможностей, а не гарантия видимости каждой записи. Она применяется и к public, и к restricted Item; выбранная row-level ветка может только сузить результат.

`Gate::before` возвращает `true` только для `admin` и `null` для остальных. Рабочие проверки используют Gate/`can()`, а не `hasPermissionTo()` и не прямые проверки роли. `hasRole('admin')` допустима только для инварианта последнего администратора и самого `Gate::before`. Прямые permissions пользователям, произвольные роли и редактор разрешений не добавляются.

Создать идемпотентный `RolesAndPermissionsSeeder`: `findOrCreate` для ролей и разрешений guard `web`, `syncPermissions` для `manager` и `user`, сброс кеша `PermissionRegistrar`. Он назначает `user` существующим пользователям без роли; если у записи несколько базовых ролей, оставляет одну наиболее привилегированную по порядку `admin > manager > user`. Запуск сидера — обязательный шаг обновления существующей installation. Новые пользователи без явно назначенной роли получают `user` после создания.

В существующем `App\Filament\Settings\Resources\UserResource` заменить множественный Select ролей на обязательный одиночный со значением `user` по умолчанию. Сохранение выполняет `syncRoles([$role])`. Создание User через REST не открывает поле роли и использует общий default. Нельзя снять роль `admin` с последнего администратора, включая самодемоцию: проверка и замена роли выполняются в одной транзакции с доступной СУБД блокировкой, отказ возвращает validation error без изменения БД. При наличии второго администратора изменение собственной роли разрешено.

Доступ к `/settings` и его пункту в user menu переводится на `settings.manage`; `ManageSettings::canAccess()` сохраняет второй барьер. Просмотр профиля User остаётся доступен всем ролям, create/update в `/settings/users` требует `users.manage`, управление группами — `groups.manage`. Назначение ролей возможно только из admin-only UI; отдельных маршрутов API, массовой выдачи `admin`, impersonation и редактора Role/Permission нет.

Passport не устанавливать: он предоставляет OAuth2 server, а не RBAC. Сохранить `laravel/sanctum`, текущие Bearer tokens и `AppServiceProvider::API_ABILITIES` без переименований.

### 2. Типизированные группы, членство и проектная привязка

Создать модель `Group` и Filament `GroupResource` в admin-only панели `/settings`. Группа содержит `name`, необязательные `description`, `parent_id` и `type`: `project`, `team`, `department`, `other`. Тип — backed enum `GroupType`; это классификация и источник предметного поведения, а не отдельные таблицы для каждого типа.

Связи и ограничения:

- `group_user`: `group_id`, `user_id`, `role` (`member` или `manager`), уникальность `(group_id, user_id)`; роль `manager` включает обычное членство и дополнительно используется Planfix-веткой для прав руководителя.
- `Group.parent_id` образует необязательную иерархию организации; циклы и самоссылка запрещены. Обычный grant на родительскую группу не распространяется автоматически на дочерние: иерархия нужна только для вычисления подчинённых руководителя в Planfix-ветке.
- `items.project_group_id` — необязательная ссылка на группу типа `project`. Это один основной проект задачи, а не board membership и не дополнительная группа доступа. Принадлежность к проекту проверяется на уровне приложения, поскольку FK не ограничивает тип связанной группы.
- Пользователь может входить в любое число групп. Удаление пользователя или группы удаляет только связи; задачи, комментарии и доски не удаляются. Группу `project` нельзя удалить, пока на неё ссылаются задачи; сначала проект у задач меняют или очищают.

Только `admin` управляет группами, составом, иерархией и настройками схем. Обычные пользователи не получают права добавить себя в разрешающую группу. REST CRUD групп и назначение ролей Spatie в объём не входят.

### 3. Два альтернативных правила доступа к Item

Независимо от ветки `null` в специальном access-поле исторической задачи означает публичность внутри приложения. Публичная задача видна всем с `items.view`, но update/delete выполняются только по глобальной матрице роли. Ограниченная задача сначала требует права `view` через `ItemAccess`; невидимую задачу нельзя изменить, удалить, прокомментировать или добавить на доску. `admin` видит и администрирует все задачи.

#### Вариант A — Jira-like: security schemes и security levels

Добавить `security_schemes`, `security_levels` и `security_level_grants`. Проектная группа ссылается на одну схему; схема переиспользуется несколькими проектами. Уровень принадлежит одной схеме, имеет название, описание и признак уровня по умолчанию (не более одного на схему). `items.security_level_id = null` означает публичную задачу, не-null — ограниченную.

Grant уровня является аддитивным правилом `subject_type + subject_id` и поддерживает:

- `all_authenticated` — любой аутентифицированный пользователь;
- `user` и `group` — конкретный пользователь или текущие непосредственные члены группы;
- `reporter`, `assignee`, `to`, `cc` — динамические участники конкретной задачи;
- `project_manager` — менеджеры `project_group_id` задачи.

Несколько grants объединяются по OR; deny-правил нет. При создании задачи применяется default level схемы выбранного проекта, при его отсутствии — публичность. При смене проекта уровень сбрасывается на default новой схемы либо на `null`, как при перемещении задачи между проектами Jira. Уровень вручную меняют `admin` или `reporter`; выбирать можно только уровень схемы текущего проекта. Для задачи без проекта доступны уровни одной выбранной администратором глобальной схемы по умолчанию.

Jira-ветка ограничивает прежде всего **видимость**. После успешного `view` действуют глобальные права `update`/`delete`; отдельные permission schemes для edit, delete, assign и transition не создаются. Это осознанный MVP-эквивалент issue security levels, а не полный перенос системы разрешений Jira.

#### Вариант B — Planfix-like: участники, группы и руководители задачи

Добавить `items.visibility` (`public` или `restricted`) и `item_group` с уникальной парой `(item_id, group_id)`. Назначенная группа выступает участником задачи: доступ получают её текущие члены без развёртывания группы в статический список пользователей. Новый член получает доступ автоматически; удалённый теряет этот путь доступа, если нет другого разрешающего правила.

Для `restricted` действует упрощённая матрица Planfix:

| Основание доступа | Просмотр и комментарии | Изменение полей / статуса | Удаление | Управление доступом |
|---|---|---|---|---|
| `admin` | да | да | да | да |
| `reporter` | да | да | да | да |
| `assignee` | да | только статус и исполнитель | нет | нет |
| `to`, `cc`, член `item_group` | да | нет | нет | нет |
| менеджер `project_group_id` (аудитор проекта) | да | да | да | нет |
| руководитель участника | наследует права этого участника | наследует | наследует | нет |

Руководитель вычисляется по `group_user.role = manager`: он получает права участников своей группы и подчинённых групп. Например, руководитель исполнителя может менять статус, а руководитель адресата — только читать и комментировать. Права нескольких оснований объединяются по максимуму. Персональных руководителей, отдельных аудиторов задачи, скрытых комментариев и права участников добавлять других участников в MVP нет.

Новые задачи в Planfix-ветке по умолчанию `restricted`: доступ уже есть у постановщика, а исполнитель, `to`, `cc`, группы и проект добавляются явно. Исторические задачи остаются `public`. Матрица участников применяется после перевода задачи в `restricted`, а глобальная матрица ролей действует всегда: например, reporter без глобального `items.delete` не удаляет даже собственную задачу, а assignee получает лишь пересечение `items.update.related` с разрешённым здесь набором полей.

### 4. Единый authorization perimeter, Filament и REST API v1

Создать приложенческий сервис `ItemAccess` с двумя формами одной row-level логики: `scopeVisibleTo(Builder, User)` для SQL-выборок и проверками `view`, `update`, `delete`, `manageAccess` для Policy. Не размножать независимые `whereHas` по страницам. `ItemPolicy` объединяет глобальное permission и `ItemAccess` по правилу **И**: ни роль `manager`, ни access grant в отдельности не разрешают операцию. `viewAny` означает лишь разрешение открыть раздел, а не видимость всех строк.

`LabelPolicy`, `BoardPolicy`, `CommentPolicy`, `UserPolicy` применяют глобальную матрицу. `BoardPolicy::update` управляет названием, колонками и порядком Board; добавление, удаление и перемещение карточки требует `ItemPolicy::update` для каждого Item и не меняет `items.status`. Проверяются автоматические Filament CRUD, bulk assign, add/remove from board, drag-and-drop, Comments package actions и REST actions. Запрещённые кнопки скрываются, но серверная проверка обязательна всегда.

Правила целостности:

- Видимость родителя и подзадачи не наследуется. Каждая запись проверяется отдельно; доступная подзадача не раскрывает название недоступного родителя, а недоступные дети исключаются из relation manager, API includes и aggregates.
- Назначить недоступный Item родителем нельзя; валидация возвращает обычную ошибку `parent_id` без раскрытия его названия. Смена видимости родителя не меняет детей.
- Комментарий доступен только при доступности родительского Item. Создание, чтение, reply, reactions, mentions и attachments в UI/API проверяют этот perimeter; правила автора или `comments.moderate` на редактирование применяются после него.
- Доступ к доске не даёт доступа к её карточкам. Скрытые Item исключаются из карточек, WIP-счётчиков, поиска добавления, массовых действий и перемещений. Сам `board_items` не становится обходным ACL.
- Изменение состава группы влияет на доступ без массового backfill. Удаление последнего разрешающего правила не блокирует задачу для её `reporter` и `admin`.
- Невидимая запись по прямому маршруту обрабатывается как отсутствующая (404); видимая запись с запрещённым действием возвращает 403. Списки и поиск просто исключают невидимые строки и не раскрывают их количество.

Scope должен выполняться SQL-запросами с подходящими индексами, без постраничной фильтрации в PHP и N+1. Административные CLI/backfill используют явный bypass сервиса, а не отключение авторизации в HTTP-коде.

В форме Item появляется секция **Access** с проектной группой и полями выбранной ветки: `security_level_id` для Jira либо `visibility` и группы для Planfix. Поля управления доступом доступны только через `manageAccess`; остальные участники не могут расширить собственные права. В infolist отображаются режим доступа, проект, уровень или назначенные группы, но не скрытые связи.

Единый scope применяется ко всем существующим поверхностям:

- `ItemResource` list/view/edit, глобальный поиск, children relation manager, bulk actions и выбор parent;
- Inbox, Sent, My Tasks, Inbox/Sent widgets и все агрегаты `StatsOverviewWidget`;
- BoardView, `AddItemsToBoard`, карточки, фильтры, WIP, действия move/remove/add;
- Favorites продолжают использовать `ItemPolicy::view`: недоступная цель не становится активной ссылкой;
- комментарии на Item и `CommentResource::perimeterQuery()`.

В REST ItemResource убрать `#[WithoutPerimeter]`, добавить тот же scope и сохранить независимые token abilities `items:read`/`items:write`. Запись требует token ability, глобальное permission и row-level доступ одновременно; роль не расширяет abilities токена, а токен не расширяет роль. В API добавляются только поля выбранной ветки и `project_group_id`; изменение access-полей проверяет `manageAccess`, а группы/уровни валидируются по допустимой схеме. Generic CRUD групп, security schemes и назначение ролей в API не добавляются. Includes `parent`, `children`, `comments` и действие `assign` работают в том же perimeter. Обновить OpenAPI snapshot и тесты 401/403/404/422.

Labels, пользователи и доски остаются общими сущностями; их списки не утверждают наличие конкретных скрытых задач.

### 5. Запись изменений и timeline Item

Установить стабильный совместимый `relaticle/activity-log`: пакет MIT поддерживает PHP 8.4+, Laravel 13, Filament 5 и Spatie Activitylog 5. Добавить его views в `resources/css/filament/admin/theme.css` и новой миграцией создать индекс `activity_log(subject_type, subject_id, created_at)`. Существующие записи и таблица сохраняются; пакет собственных миграций не требует.

`Item` реализует `HasTimeline` через `InteractsWithTimeline`, строит timeline из `fromActivityLog()` и получает `ActivityLogAction` на `ViewItem`. Доступ к action совпадает с `ItemPolicy::view`, поэтому restricted perimeter нельзя обойти через историю. История открывается в slide-over и не дублирует inline-комментарии. Показываются дата, causer, событие и diff старых/новых значений. Position-only изменения и перемещения `board_items` не попадают в ленту.

Запись ведётся по allowlist для каждой модели с `logOnlyDirty()` и пропуском пустых изменений:

- Item сохраняет текущие отслеживаемые поля плюс `project_group_id` и поля выбранной access-ветки; `position` остаётся исключён. Изменения `item_group` и access grants пишутся событием `access_updated`.
- User логирует только `name`, `email`; изменение роли пишется отдельным `roles_updated` с old/new и causer администратора.
- Group логирует `name`, `description`, `parent_id`, `type`; изменение состава пишется `group_members_updated` с идентификаторами добавленных/удалённых пользователей и их group roles.
- Label — `name`, `color`; Board — `name`, `description`; BoardColumn — `name`, `color`, `wip_limit`.
- Comment — `body`, `edited_at`, `pinned_at`; создание, изменение и удаление получают собственный subject Comment.
- Изменение General settings пишется вручную `settings_updated` только для явного списка безопасных ключей формы.

`password`, `remember_token`, API tokens, секреты, attachment contents и технические positions никогда не включаются в properties. Дополнительно зарегистрировать обёртку над стандартным renderer, которая маскирует эти ключи в `attributes` и `old`, даже если запись появилась из старого или стороннего источника. Кеширование timeline, связанные feeds, экспорт и уведомления не включаются.

### 6. Общий журнал в панели настроек

Добавить приложению модель Activity, наследующую configured Spatie Activity model, и `App\Filament\Settings\Resources\ActivityResource` с маршрутом `/settings/activity-log`. Ресурс содержит только List и View: Create/Edit/Delete, bulk delete и произвольная запись через UI отсутствуют. Навигация и обе страницы требуют `activity.view`; не-администратор дополнительно отсекается `canAccessPanel()`.

Список по умолчанию сортируется по `created_at DESC`, выводит дату, causer, event, log name, subject type/ID и description. Предусмотреть фильтры по диапазону дат, event, causer, subject type и log name, eager load causer/subject и пагинацию. View показывает properties в виде old/new diff через тот же защищённый renderer; удалённый subject отображается как сохранённые type/ID без битой ссылки. Данные до внедрения не синтезируются: журнал показывает только реально сохранённую историю.

Политика очистки остаётся существующей (`activitylog.clean_after_days = 365`); scheduler, экспорт и API аудита не добавляются.

### 7. Миграция, выпуск и проверка безопасности

Все изменения схемы выполняются новыми миграциями. Исторические Item получают `security_level_id = null` либо `visibility = public`, поэтому первый deploy не скрывает данные; их операции далее ограничиваются новой глобальной матрицей. `RolesAndPermissionsSeeder` запускается до включения новых policies и нормализует роли без потери административного доступа. В Planfix-ветке default `restricted` применяется на уровне формы/доменного создания новых записей, а не массовым backfill. Демонстрационные seeders создают примеры проекта, команды и подразделения, но тесты не зависят от demo users.

Перед выпуском выбранная ветка документируется в `docs/specs/`: модель групп, глобальная и row-level матрицы, default для новых задач, поведение связей, API и аудит. Обновляются `settings-panel.md`, `boards.md`, `item-comments.md`, `rest-api.md`, Roadmap и утверждение об activity logging в `AGENTS.md`. Откат кода не должен удалять исходные Item или `activity_log`; новые таблицы и access-поля не используются старой версией.

Обязательна матрица Pest-тестов «роль × основание доступа × операция» и сквозные HTTP/Livewire-тесты двух пользователей. Отдельно проверяются динамическое добавление/удаление члена группы, иерархия руководителей, смена проекта/уровня, независимая видимость подзадач, отсутствие скрытых ID и счётчиков, совместимость публичных исторических записей, `php artisan rest:check`, OpenAPI snapshot, Pint, полный `php artisan test` и frontend build.

## Дорожная карта

1. **Глобальные роли и их назначение.** Добавить enums, permissions, seeder, Gate, одиночную роль в UserResource и защиту последнего администратора. Прогнать backfill на копии БД и выпустить этот фундамент до ограничения операций.

4. **Authorization perimeter, Filament и REST.** Реализовать пересечение global permissions и `ItemAccess`, policies, SQL scopes, Access UI и правила связей; подключить все рабочие поверхности, API и OpenAPI.

Этапы 1–4 образуют один security release: нельзя включать policies до нормализации ролей и нельзя выпускать две access-ветки одновременно. Этап 6 зависит от записи событий этапа 5; откат UI не удаляет `activity_log` или его историю.

## Итого и рекомендации

Использовать Spatie Permission как глобальный верхний предел действий, policies и `ItemAccess` как обязательное пересечение правил, а Sanctum как независимый барьер API; Passport внедрять только отдельным OAuth2-решением. Для row-level доступа выбрать **Planfix-like** модель: типизированные группы назначаются участниками конкретной задачи, руководители и аудиторы проекта расширяют доступ без сложной настройки схем. Jira-like целесообразен при обязательных переиспользуемых security schemes. В обоих случаях критичен единый SQL/Policy perimeter для UI, связей и REST API. Изменения ролей, групп, доступа и доменных записей сохраняются в одном Spatie activity log, отображаются в авторизованном timeline Item и admin-only read-only аудите с обязательной маскировкой секретов.

### Открытые вопросы

- **Выбор ветки перед delivery:** решено в пользу рекомендованной Planfix-like модели; Jira-like schemes не реализуются и остаются границей отклонённого варианта. Одновременная поддержка обоих режимов и переключатель в runtime не планируются.
- **Конфиденциальность файлов:** текущие item description и comment attachments используют публичные disk URL. Row-level ACL не защищает файл по известной ссылке; signed URLs/private disk требуют отдельного RFC и не должны считаться закрытыми этой задачей.
- **Противоречие текущей спеки:** [item-comments.md](../../specs/item-comments.md) в «Key decisions» называет attachments выключенными, а в «Known limitations» — включёнными. Перед delivery уточнить спецификацию; фактическая защита вложений в любом случае остаётся отдельным вопросом.
- **Скрытые проекты как отдельный раздел:** сейчас проект — типизированная группа без собственного рабочего UI. Отдельные project pages, списки открытых/скрытых проектов и default participants проекта не входят в этот RFC.
- **Хранение журнала:** нужно ли запускать `activitylog:clean` по расписанию и какой срок хранения требуется в production? Текущий параметр 365 дней сохраняется, но scheduler и экспорт перед очисткой требуют отдельного эксплуатационного решения.

### Альтернативные варианты

| Критерий | A — Jira-like | B — Planfix-like (рекомендуется) |
|---|---|---|
| Основная единица настройки | Схема и именованный уровень | Конкретная задача и её участники |
| Групповой доступ | Grant уровня на текущих членов группы | Группа — динамический участник задачи |
| Права операций | Глобальные permissions после view | Матрица участников restricted Item поверх глобальной роли |
| Переиспользование политик | Высокое | Через проект/группы, без отдельных схем |
| Сложность администрирования | Выше: schemes, levels, grants, defaults | Ниже: участники, группы, restricted/public |
| Соответствие текущему коду | Требует новой подсистемы | Использует существующие participant relations |
| Основной риск | Ложное ощущение полного Jira RBAC без permission schemes | Изменение прав при переходе public → restricted |

Дополнительные архитектурные альтернативы:

- **Passport вместо Sanctum** даёт OAuth2 authorization server и сторонние grant flows, но требует миграции аутентификации; для first-party Bearer tokens и RBAC преимуществ не даёт.
- **Проверки ролей вместо разрешений** проще на старте, но смешивают названия ролей с бизнес-правилами. Выбраны permissions через Gate.
- **Только общий журнал без Relaticle timeline** дешевле по UI, но оставляет историю Item доступной только администратору. Выбраны оба представления над одним хранилищем.

### Эталонная модель Redmine (справочно)

Redmine не участвует в выборе ветки, но полезен как контрольный пример: он показывает, чего стоит ожидать, если ограничивать доступ только членством в группе, без уровня у самой задачи.

**Где живут права.** У задачи Redmine нет собственного ACL. Права назначены роли (`Administration → Roles and permissions`) и действуют только в тех проектах, где пользователь получил эту роль; одна и та же роль в разных проектах даёт разный результат, а несколько ролей складываются. Роли `Non member` и `Anonymous` системные: они применяются автоматически и только к публичным проектам. Приватный проект целиком скрыт от не-членов.

**Роль группы.** Группа — объединение пользователей, которому роль выдаётся сразу всем участникам проекта; отдельного «группового» perimeter задач у неё нет. Задачу можно назначить на группу (при включённой настройке), и тогда она попадает в «назначенные мне» у всех участников, пока кто-то не возьмёт её на себя. Права групп аддитивны и не пересекаются.

**Видимость внутри проекта.** У роли фиксированный набор вариантов: все задачи; все не-приватные (по умолчанию, плюс приватные, где пользователь автор или исполнитель); только созданные или назначенные пользователю. Приватная задача доступна автору, исполнителю, наблюдателям и тем, у кого есть право на приватные задачи. Варианта «задачи коллег из моей группы, но не чужих групп» в стандартной поставке нет.

**Как изолируют команды.** Отдельными проектами и подпроектами под каждую команду, отдельными ролями под разные подмножества пользователей (внутренние и внешние исполнители), либо плагином `Redmine_Group_Issues_Visibility`, который добавляет видимость по группе. Ограничение списка исполнителей группой или ролью отдельной функцией не делается: она уже выражается свойством роли «задачи можно назначать на эту роль».

**Что это подтверждает в RFC.** `project_group_id` соответствует приватному проекту Redmine и отвечает за принадлежность задачи, но не заменяет уровень доступа: без атрибута у задачи Redmine вынужден дробить работу на проекты или ставить плагин. Поэтому обе ветки RFC сохраняют уровень именно у задачи (`security_level_id` либо `visibility`) и получают права из оснований доступа, а не только из членства в группе.
