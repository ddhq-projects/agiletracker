# Отдельная панель настроек и кастомные поля Item

## TL DR

Выносим общие настройки, управление пользователями и определения кастомных полей в отдельную Filament-панель `/settings`, доступную только администраторам. Для Item подключаем `relaticle/custom-fields` 3.x: администраторы управляют схемой полей без новых миграций, а существующие `meta` и публичное поле API `type` переносятся без потери данных и изменения контракта API v1.

## Контекст

### Что?

Сейчас `ManageSettings` — страница основной панели `main` с URL `/settings`, а `UserResource` находится там же в группе Settings. `Item` хранит произвольные данные в JSON-колонке `meta`; API v1 представляет `meta.type` как виртуальное поле `type`. Пакет Custom Fields ещё не установлен.

Предлагается создать отдельную панель `settings` с базовым путём `/settings`, перенести туда `ManageSettings` и `UserResource`, а управление полями Item реализовать через `relaticle/custom-fields`. Этот RFC заменяет этап 3 документа [Relaticle Kanban, Comments, and Item Custom Fields](2026-11-14-relaticle-item-features.md) и уточняет размещение настроек из [Central Settings System](2026-05-30-settings-system.md); уже завершённые этапы Kanban и Comments не меняются.

### Зачем?

Административная конфигурация смешана с рабочими разделами, а добавление каждого нового атрибута Item сейчас требует изменения формы, модели и JSON-схемы. Отдельная панель создаёт понятную административную границу, а Custom Fields позволяет администратору расширять Item без релиза кода. При этом статус, метки, доски, права и API не должны измениться как побочный эффект.

### Как?

Новый `SettingsPanelProvider` регистрирует только административные страницы и ресурсы; `User::canAccessPanel()` ограничивает всю панель ролью `admin`. Custom Fields подключается к этой панели для управления определениями, а builders пакета добавляются в существующий `ItemResource` основной панели. Миграция переносит `meta` в значения Custom Fields, а REST-адаптер сохраняет виртуальное поле `type` поверх нового хранилища.

## Назначение и цели

- Дать администратору отдельную точку входа для общих настроек, пользователей и схемы полей Item.
- Сохранить существующий URL `/settings` для общих настроек и не дать обычным пользователям доступ к административной панели.
- Позволить создавать, редактировать, просматривать и фильтровать значения кастомных полей Item через Filament.
- Перенести все поддерживаемые значения `meta` и `type` без потерь и повторного создания данных.
- Сохранить поля, маршруты, валидацию и авторизацию REST API v1.

Заинтересованные стороны: администраторы, пользователи Item, клиенты API v1, maintainers, а также ревьюеры архитектуры, безопасности и лицензирования.

## Составляющие и особенности

### 1. Отдельная панель настроек и доступ

Создать `App\Providers\Filament\SettingsPanelProvider` с идентификатором `settings` и `path('settings')`, зарегистрировать его в `bootstrap/providers.php`. Панель использует существующую аутентификацию Laravel, общую Filament-тему и стандартные middleware основной панели, но не становится панелью по умолчанию и не обнаруживает рабочие ресурсы основной панели. Панель включает собственный вход `/settings/login`: Filament перенаправляет гостя на login-маршрут текущей панели, и без него редирект остаётся без адреса.

Перенести `ManageSettings` в namespace и каталог, обнаруживаемый только новой панелью. Назначить странице корневой маршрут панели, чтобы General оставался доступен именно по `/settings`, а не по `/settings/settings`. Форма продолжает использовать `GeneralSettings` и `spatie/laravel-settings`; миграция её значений не требуется.

Перенести `UserResource` и его страницы в новую панель. Управление пользователями получает URL внутри `/settings`; существующая `UserPolicy` продолжает ограничивать создание и редактирование администраторами. `LabelResource` остаётся в Collections основной панели.

В `User::canAccessPanel()` разрешить `main` всем аутентифицированным пользователям, а `settings` — только роли `admin`. Сохранить `ManageSettings::canAccess()` и `CustomFieldsPlugin::authorize()` как дополнительную проверку на уровне страниц. Гость перенаправляется на вход; аутентифицированный не-администратор получает 403 на любом маршруте панели.

В основной панели удалить старые пункты General и Users из навигации. Пункт Settings вынести из сайдбара в пользовательское меню (шапка) и показывать только администратору; ссылку GitHub из основной панели убрать и разместить её в навигации панели `settings`. В самой панели `settings` добавить обратный путь в шапку и в навигацию: кнопка «Back to app» ведёт на главную страницу основной панели. Не реактивировать отключённый legacy `App\Filament\Pages\Settings`: миграция или удаление `AppSetting` и таблицы `app_settings` в объём не входят.

### 2. Установка Custom Fields и управление определениями

До установки зафиксировать лицензионное решение. Рекомендуется коммерческая лицензия: проект распространяется под MIT, а AGPL-3.0 требует отдельного согласования условий распространения. Установить стабильный `relaticle/custom-fields:^3.0` из приватного Composer-репозитория; лицензионный ключ и `auth.json` не коммитить. Выполнить `custom-fields:install`, применить миграции пакета и добавить его views в `resources/css/filament/admin/theme.css`.

Зарегистрировать `CustomFieldsPlugin` в панели `settings` с `authorize()`, разрешающим доступ только администратору. В этой панели администратор управляет определениями полей Item; в основной панели отдельного пункта управления полями нет. Системные определения нельзя удалить через UI. Пользователи без роли `admin` работают только со значениями полей в рамках существующих прав `ItemPolicy`.

Multi-tenancy, импорт/экспорт и file-upload поля не включаются. Кастомные поля для других моделей, собственные типы полей и шифрование значений также вне объёма.

### 3. Поля Item и перенос `meta`

`App\Models\Item` реализует `HasCustomFields` и использует `UsesCustomFields`. В `ItemResource` добавить `CustomFields::form()`, `::table()` и `::infolist()` так, чтобы поля отображались при создании, редактировании и просмотре Item, а поддерживаемые пакетом колонки и фильтры — в таблице. Изменения значений кастомных полей попадают в activity log; изменения `position` по-прежнему не логируются.

Создать системное поле `type` типа select с кодом `type` и строковыми опциями `task`, `bug`, `feature`. Оно заменяет `meta.type`, но не связано с нативным `items.status`, флагом `is_epic` или метками. Новые записи получают `type` по действующим правилам формы и API; статус и позиционирование Item остаются прежними.

Миграция создаёт текстовые поля в секции Additional information для остальных ключей `meta` и копирует значения каждого Item. Коды полей — стабильные snake_case; пустые или конфликтующие коды получают детерминированный hash-суффикс, а исходный ключ сохраняется как имя поля. Неподдерживаемые не-scalar значения не преобразуются молча: миграция останавливается с идентификатором Item и именем ключа. Legacy-значения `type` вне стандартных трёх опций сохраняются как дополнительные legacy-опции, но новые API-записи принимают только `task`, `bug`, `feature`.

После успешного backfill удалить KeyValue UI и все runtime-чтения/записи `items.meta`, включая фабрики и seeders. Саму колонку сохранить минимум на один релиз как резервную копию для rollback; она больше не является источником истины и исключается из fillable, casts и конфигурации activity log. Повторный запуск переноса не должен дублировать определения или значения.

### 4. Совместимость REST API v1

`App\Rest\Resources\ItemResource` сохраняет виртуальное поле `type`, его маршруты, обязательность при создании, валидацию и фильтры `=`/`!=`. Чтение возвращает значение системного custom field; запись выполняется после создания Item внутри той же транзакции. Фильтрация использует типизированное `custom_field_values.string_value` через связь с определением `type`, а не JSON `meta`.

Другие кастомные поля и произвольный `meta` в API v1 не предоставляются. Не добавлять generic CRUD для определений или значений Custom Fields. Обновить реализацию и описание хранения, не меняя публичную схему OpenAPI; существующие права token abilities и `ItemPolicy` остаются без изменений.

### Общие ограничения

Не менять `items.status`, labels, boards, comments, soft deletes и структуру `items.position`. Не удалять `items.meta`, не добавлять per-user settings, отдельный auth guard или multi-tenancy. Панель настроек можно выпустить независимо; установка Custom Fields, перенос Item и REST-адаптер поставляются одним релизом после решения о лицензии.

## Критерии приемки (checklist)

### 1. Отдельная панель настроек и доступ

- [x] Администратор получает 200 на `/settings`, видит General и Users в новой панели и может сохранить `GeneralSettings`; не-администратор получает 403, гость перенаправляется на вход.
- [x] `/settings` открывает General без повторного сегмента `settings`, а Users находится внутри той же панели.
- [x] В основной панели нет старых пунктов General/Users; пункт Settings находится в пользовательском меню, виден только администратору и ведёт в новую панель; ссылка GitHub есть только в панели `settings`.
- [x] В шапке и в навигации панели `settings` есть кнопка «Back to app», возвращающая на главную страницу основной панели.
- [x] Основная панель, Labels и существующие сценарии работы с Item доступны не-администраторам по прежним правилам.

### 2. Установка Custom Fields и управление определениями

- [ ] Выбранный лицензионный режим задокументирован, секреты отсутствуют в Git, `relaticle/custom-fields:^3.0` и его миграции установлены без конфликтов с PHP 8.4+, Laravel 13 и Filament 5.
- [ ] Администратор может создать, изменить и удалить пользовательское определение поля Item в `/settings`; системное поле удалить через UI нельзя.
- [ ] Не-администратор не видит управление определениями и получает 403 при прямом обращении к его маршрутам.
- [ ] Production Vite build содержит стили Custom Fields; multi-tenancy, import/export и file-upload поля не доступны.

### 3. Поля Item и перенос `meta`

- [ ] Пользователь с правом обновления Item может заполнить, просмотреть и отфильтровать значения кастомных полей; пользователь без права обновления не может их изменить.
- [ ] Системный `type` поддерживает `task`, `bug`, `feature`, а изменения custom-field values создают activity records без записей для position-only изменений.
- [ ] Тест миграции подтверждает сохранение каждого поддерживаемого `meta`-значения, стабильность кодов, идемпотентность и явный abort на не-scalar данных.
- [ ] Legacy `type` читается без потерь; после переноса runtime-код, формы, фабрики и seeders не используют `items.meta`, а колонка сохранена для rollback.

### 4. Совместимость REST API v1

- [ ] HTTP-тесты создания, чтения, обновления и фильтрации Item по `type` проходят на Custom Fields, включая откат транзакции при ошибке записи значения.
- [ ] API принимает только `task`, `bug`, `feature` для новых записей и корректно читает сохранённые legacy-опции.
- [ ] API v1 не exposingует другие custom fields или `meta`; `php artisan rest:check` и snapshot-тест OpenAPI проходят без непреднамеренных изменений контракта.
- [ ] Для всех блоков проходят focused Pest tests, полный `php artisan test`, Pint и `npm run build`.

## Дорожная карта

1. **Отдельная панель настроек и доступ.** Создать provider, перенести General/Users, настроить маршруты, навигацию и `canAccessPanel()`, обновить feature-тесты. Этот этап не зависит от Custom Fields.
2. **Установка Custom Fields и управление определениями.** После лицензионного решения установить пакет, миграции и стили, подключить admin-only plugin в новой панели.
3. **Поля Item и перенос `meta`.** Подключить модель и ItemResource, создать системный `type`, реализовать и проверить идемпотентный backfill на копии реальных данных.
4. **Совместимость REST API v1.** Перевести виртуальное `type` на Custom Fields, прогнать HTTP/OpenAPI проверки и выпустить этапы 2–4 одним релизом. Колонку `meta` удалять только отдельным последующим решением после production verification.

## Итого и рекомендации

Создать отдельную admin-only панель `/settings` и разместить в ней General, Users и Custom Fields. Использовать Custom Fields как единственное хранилище динамических атрибутов Item после контролируемой миграции `meta`, сохранив нативный workflow и REST `type`. Начинать установку пакета только после явного выбора лицензии.

### Открытые вопросы

- **Лицензия Custom Fields:** maintainer приобретает коммерческую лицензию либо отдельно принимает AGPL-3.0 и её обязательства? До ответа этапы 2–4 заблокированы; этап 1 можно реализовывать.

### Альтернативные варианты

- **Оставить страницы в основной панели.** Меньше изменений в маршрутах и навигации, но не достигается отдельная административная зона из Roadmap.
- **Собственная schema-driven система полей поверх JSON.** Не требует лицензии и внешней EAV-схемы, но переносит на проект поддержку определений, валидации, Filament UI, фильтров и миграций, которые уже даёт Custom Fields.
- **Оставить `meta` без миграции.** Сохраняет текущую реализацию, но не даёт администратору управляемой схемы и типизированных значений; не решает задачу.
