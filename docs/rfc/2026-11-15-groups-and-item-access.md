# Группы пользователей и ограничение доступа к задачам

## TL DR

Сейчас любой аутентифицированный пользователь AgileTracker видит и изменяет все задачи, а существующие роли участников не влияют на авторизацию. Предлагается добавить типизированные группы и два проработанных варианта ограничения доступа: **Jira-like** с переиспользуемыми схемами и уровнями безопасности либо **Planfix-like** с доступом участников, групп и руководителей к конкретной задаче. Рекомендуется Planfix-like вариант: он опирается на уже существующие `reporter`, `assignee`, `to` и `cc`, проще в настройке и автоматически учитывает изменения состава групп; Jira-like остаётся альтернативой для сценариев с переиспользуемыми политиками безопасности.

## Контекст

**Situation.** В `ItemPolicy` методы `view`, `create`, `update` и `delete` разрешены всем аутентифицированным пользователям. Спецификация [REST API v1](../specs/rest-api.md) подтверждает, что Item не имеет perimeter-фильтра, а [Boards](../specs/boards.md) прямо фиксирует плоский доступ. При этом у Item уже есть постановщик (`reporter_id`), исполнитель (`assignee_id`), адресаты (`item_to`) и наблюдатели (`item_cc`), а роли Spatie `admin`, `manager`, `user` пока не образуют предметную модель прав на задачи.

**Complication.** Без групп и row-level visibility нельзя разделить проекты, команды и подразделения: скрытие записи только в Filament-таблице оставит её в API, на досках, в комментариях, виджетах и по прямой ссылке. Для Jira характерны permission schemes и независимые issue security schemes; для Planfix — доступ к каждой задаче по её участникам, группам, аудиторам и руководителям.

**Question.** Как добавить группы типов `project`, `team`, `department` и других и ограничить задачи без рассинхронизации Filament, REST и смежных сущностей?

**Answer.** Ввести общую доменную модель групп, единый сервис видимости Item и один из двух альтернативных механизмов доступа. Оба варианта описаны ниже как ветки одного RFC; в delivery реализуется только выбранная ветка, а не два параллельных движка авторизации. Базовая рекомендация — Planfix-like.

## Назначение и цели

- Дать администратору управляемые группы пользователей с типами и составом, пригодные для проектов, команд и подразделений.
- Позволить ограничить видимость конкретной задачи группами и существующими участниками, сохранив понятные права на чтение, комментирование, изменение и удаление.
- Централизовать авторизацию так, чтобы список, карточка, вложенные связи, доски, комментарии, дашборд, глобальный поиск и REST API возвращали согласованный результат.
- Не менять существующую видимость исторических задач до явной настройки ограничений и не смешивать доступ с workflow status, labels и board membership.
- Зафиксировать два эталонных варианта и критерии выбора до реализации.

Заинтересованные стороны: администраторы, руководители групп, постановщики и исполнители задачи, обычные пользователи, клиенты REST API v1, maintainers и ревьюеры безопасности. Ревью требуется продуктовое (выбор Jira/Planfix-модели), архитектурное и по безопасности (полнота perimeter-фильтров).

## Составляющие и особенности

### 1. Типизированные группы, членство и проектная привязка

Создать модель `Group` и Filament `GroupResource` в admin-only панели `/settings`. Группа содержит `name`, необязательные `description`, `parent_id` и `type`: `project`, `team`, `department`, `other`. Тип — backed enum `GroupType`; это классификация и источник предметного поведения, а не отдельные таблицы для каждого типа.

Связи и ограничения:

- `group_user`: `group_id`, `user_id`, `role` (`member` или `manager`), уникальность `(group_id, user_id)`; роль `manager` включает обычное членство и дополнительно используется Planfix-веткой для прав руководителя.
- `Group.parent_id` образует необязательную иерархию организации; циклы и самоссылка запрещены. Обычный grant на родительскую группу не распространяется автоматически на дочерние: иерархия нужна только для вычисления подчинённых руководителя в Planfix-ветке.
- `items.project_group_id` — необязательная ссылка на группу типа `project`. Это один основной проект задачи, а не board membership и не дополнительная группа доступа. Принадлежность к проекту проверяется на уровне приложения, поскольку FK не ограничивает тип связанной группы.
- Пользователь может входить в любое число групп. Удаление пользователя или группы удаляет только связи; задачи, комментарии и доски не удаляются. Группу `project` нельзя удалить, пока на неё ссылаются задачи; сначала проект у задач меняют или очищают.

Только `admin` управляет группами, составом, иерархией и настройками схем. Обычные пользователи не получают права добавить себя в разрешающую группу. REST CRUD групп и назначение ролей Spatie в объём не входят.

### 2. Два альтернативных правила доступа к Item

Независимо от ветки `null` в специальном access-поле исторической задачи означает публичность внутри приложения. Публичная задача сохраняет текущие права аутентифицированных пользователей. Ограниченная задача сначала требует права `view`; невидимую задачу нельзя изменить, удалить, прокомментировать или добавить на доску. `admin` видит и администрирует все задачи.

#### Вариант A — Jira-like: security schemes и security levels

Добавить `security_schemes`, `security_levels` и `security_level_grants`. Проектная группа ссылается на одну схему; схема переиспользуется несколькими проектами. Уровень принадлежит одной схеме, имеет название, описание и признак уровня по умолчанию (не более одного на схему). `items.security_level_id = null` означает публичную задачу, не-null — ограниченную.

Grant уровня является аддитивным правилом `subject_type + subject_id` и поддерживает:

- `all_authenticated` — любой аутентифицированный пользователь;
- `user` и `group` — конкретный пользователь или текущие непосредственные члены группы;
- `reporter`, `assignee`, `to`, `cc` — динамические участники конкретной задачи;
- `project_manager` — менеджеры `project_group_id` задачи.

Несколько grants объединяются по OR; deny-правил нет. При создании задачи применяется default level схемы выбранного проекта, при его отсутствии — публичность. При смене проекта уровень сбрасывается на default новой схемы либо на `null`, как при перемещении задачи между проектами Jira. Уровень вручную меняют `admin` или `reporter`; выбирать можно только уровень схемы текущего проекта. Для задачи без проекта доступны уровни одной выбранной администратором глобальной схемы по умолчанию.

Jira-ветка ограничивает прежде всего **видимость**. После успешного `view` действуют существующие права `update`/`delete`; отдельные permission schemes для edit, delete, assign и transition не создаются. Это осознанный MVP-эквивалент issue security levels, а не полный перенос системы разрешений Jira.

#### Вариант B — Planfix-like: участники, группы и руководители задачи

Добавить `items.visibility` (`public` или `restricted`) и `item_group` с уникальной парой `(item_id, group_id)`. Назначенная группа выступает участником задачи: доступ получают её текущие члены без развёртывания группы в статический список пользователей. Новый член получает доступ автоматически; удалённый теряет этот путь доступа, если нет другого разрешающего правила.

Для `restricted` действует упрощённая матрица Planfix:

| Основание доступа | Просмотр и комментарии | Изменение полей / статуса | Удаление | Управление доступом |
|---|---|---|---|---|
| `admin` | да | да | да | да |
| `reporter` | да | да | да | да |
| `assignee` | да | только статус и исполнитель | нет | нет |
| `to`, `cc`, член `item_group` | да | нет | нет | нет |
| менеджер `project_group_id` (аудитор проекта) | да | да | да | нет |
| руководитель участника | наследует права этого участника | наследует | наследует | нет |

Руководитель вычисляется по `group_user.role = manager`: он получает права участников своей группы и подчинённых групп. Например, руководитель исполнителя может менять статус, а руководитель адресата — только читать и комментировать. Права нескольких оснований объединяются по максимуму. Персональных руководителей, отдельных аудиторов задачи, скрытых комментариев и права участников добавлять других участников в MVP нет.

Новые задачи в Planfix-ветке по умолчанию `restricted`: доступ уже есть у постановщика, а исполнитель, `to`, `cc`, группы и проект добавляются явно. Исторические задачи остаются `public`. Публичная задача намеренно сохраняет прежнюю permissive-модель, поэтому матрица ролей применяется только после перевода задачи в `restricted`.

### 3. Единый authorization perimeter и правила связанных записей

Создать приложенческий сервис `ItemAccess` с двумя формами одной логики: `scopeVisibleTo(Builder, User)` для SQL-выборок и проверками `view`, `update`, `delete`, `manageAccess` для Policy. Не размножать независимые `whereHas` по страницам. `ItemPolicy` делегирует сервису; `viewAny` означает лишь разрешение открыть раздел, а не видимость всех строк.

Правила целостности:

- Видимость родителя и подзадачи не наследуется. Каждая запись проверяется отдельно; доступная подзадача не раскрывает название недоступного родителя, а недоступные дети исключаются из relation manager, API includes и aggregates.
- Назначить недоступный Item родителем нельзя; валидация возвращает обычную ошибку `parent_id` без раскрытия его названия. Смена видимости родителя не меняет детей.
- Комментарий доступен только при доступности родительского Item. Создание, чтение, reply, reactions, mentions и attachments в UI/API проверяют этот perimeter; правила автора/admin на редактирование комментария применяются после него.
- Доступ к доске не даёт доступа к её карточкам. Скрытые Item исключаются из карточек, WIP-счётчиков, поиска добавления, массовых действий и перемещений. Сам `board_items` не становится обходным ACL.
- Изменение состава группы влияет на доступ без массового backfill. Удаление последнего разрешающего правила не блокирует задачу для её `reporter` и `admin`.
- Невидимая запись по прямому маршруту обрабатывается как отсутствующая (404); видимая запись с запрещённым действием возвращает 403. Списки и поиск просто исключают невидимые строки и не раскрывают их количество.

Scope должен выполняться SQL-запросами с подходящими индексами, без постраничной фильтрации в PHP и N+1. Административные CLI/backfill используют явный bypass сервиса, а не отключение авторизации в HTTP-коде.

### 4. Согласованные Filament и REST API v1

В форме Item появляется секция **Access** с проектной группой и полями выбранной ветки: `security_level_id` для Jira либо `visibility` и группы для Planfix. Поля управления доступом доступны только через `manageAccess`; остальные участники не могут расширить собственные права. В infolist отображаются режим доступа, проект, уровень или назначенные группы, но не скрытые связи.

Единый scope применяется ко всем существующим поверхностям:

- `ItemResource` list/view/edit, глобальный поиск, children relation manager, bulk actions и выбор parent;
- Inbox, Sent, My Tasks, Inbox/Sent widgets и все агрегаты `StatsOverviewWidget`;
- BoardView, `AddItemsToBoard`, карточки, фильтры, WIP, действия move/remove/add;
- Favorites продолжают использовать `ItemPolicy::view`: недоступная цель не становится активной ссылкой;
- комментарии на Item и `CommentResource::perimeterQuery()`.

В REST ItemResource убрать `#[WithoutPerimeter]`, добавить тот же scope и сохранить независимые token abilities `items:read`/`items:write`. В API добавляются только поля выбранной ветки и `project_group_id`; изменение access-полей проверяет `manageAccess`, а группы/уровни валидируются по допустимой схеме. Generic CRUD групп и security schemes в API не добавляется. Includes `parent`, `children`, `comments` и действие `assign` работают в том же perimeter. Обновить OpenAPI snapshot и тесты 401/403/404/422: token ability не заменяет Policy, а Policy не заменяет ability.

Labels, пользователи и доски остаются общими сущностями; их списки не утверждают наличие конкретных скрытых задач. Activity log доступен только внутри уже авторизованной карточки Item.

### 5. Миграция, выпуск и проверка безопасности

Все изменения схемы выполняются новыми миграциями. Исторические Item получают `security_level_id = null` либо `visibility = public`, поэтому первый deploy не скрывает данные и не меняет прежние права. В Planfix-ветке default `restricted` применяется на уровне формы/доменного создания новых записей, а не массовым backfill. Демонстрационные seeders создают примеры проекта, команды и подразделения, но тесты не зависят от demo users.

Перед выпуском выбранная ветка документируется в `docs/specs/`: модель групп, матрица прав, default для новых задач, поведение связей и API. Roadmap обновляется после реализации. Откат кода не должен удалять исходные Item; новые таблицы и access-поля не используются старой версией.

Обязательна матрица Pest-тестов «роль × основание доступа × операция» и сквозные HTTP/Livewire-тесты двух пользователей. Отдельно проверяются динамическое добавление/удаление члена группы, иерархия руководителей, смена проекта/уровня, независимая видимость подзадач, отсутствие скрытых ID и счётчиков, совместимость публичных исторических записей, `php artisan rest:check`, OpenAPI snapshot, Pint, полный `php artisan test` и frontend build.

## Критерии приемки (checklist)

### 1. Типизированные группы, членство и проектная привязка

- [ ] Администратор создаёт и редактирует группы всех четырёх типов, назначает members/managers и родительскую группу; не-администратор получает 403 на управление.
- [ ] Состав many-to-many уникален, циклы иерархии отклоняются, `project_group_id` принимает только `project`, а занятую проектную группу нельзя удалить.
- [ ] Удаление членства не меняет Item и не требует backfill доступа.

### 2. Два альтернативных правила доступа к Item

- [ ] **Общее:** историческая публичная задача сохраняет прежние права; ограниченная задача без разрешающего правила недоступна, а `admin` и положенный `reporter` не теряют доступ.
- [ ] **A:** схема переиспользуется проектами, default уровень уникален, все заявленные subject types работают по OR, смена проекта применяет правило новой схемы.
- [ ] **A:** не-член уровня не видит ограниченный Item даже при доступности проекта; управлять схемами может только admin, менять уровень — admin или reporter.
- [ ] **B:** член назначенной группы получает доступ динамически; добавление и удаление пользователя меняют доступ без изменения `item_group`.
- [ ] **B:** каждая строка матрицы прав подтверждена тестом, включая project manager и руководителей подчинённых групп; новые задачи по умолчанию restricted.

### 3. Единый authorization perimeter и правила связанных записей

- [ ] `ItemPolicy` и все query scopes используют один сервис; прямой доступ к невидимому Item даёт 404, запрещённое действие над видимым — 403.
- [ ] Невидимый Item нельзя обновить, удалить, назначить, прокомментировать или добавить на доску через отдельный endpoint/action.
- [ ] Родитель и дети проверяются независимо; скрытый родитель не раскрывается, скрытые дети отсутствуют в includes/aggregates, назначение скрытого parent отклоняется.
- [ ] Комментарии и доски не показывают скрытые Item и их счётчики; выборки не используют PHP post-filtering и не содержат N+1.

### 4. Согласованные Filament и REST API v1

- [ ] Access UI показывает только поля выбранной ветки и не позволяет пользователю без `manageAccess` изменить их или расширить свои права.
- [ ] Два пользователя с разными правами получают согласованные результаты в Item list/view/search, Inbox/Sent, widgets, Favorites, boards и comments.
- [ ] REST search/mutate/destroy/assign, parent/children/comments includes применяют тот же perimeter; token abilities продолжают проверяться отдельно.
- [ ] OpenAPI содержит только additive-поля выбранной ветки; generic group/scheme API отсутствует, существующие публичные поля и маршруты не сломаны.

### 5. Миграция, выпуск и проверка безопасности

- [ ] Миграция на копии существующих данных оставляет все исторические Item публичными, повторный запуск не дублирует grants/связи, новые индексы присутствуют.
- [ ] Спецификация и Roadmap соответствуют выбранной реализации; не выбранная ветка не оставляет второго runtime-механизма авторизации.
- [ ] Проходят матричные и сквозные Pest-тесты, полный `php artisan test`, `php artisan rest:check`, Pint и `npm run build`.

## Дорожная карта

1. **Группы и проектная привязка.** Создать модели, миграции, enum, relations, admin-only GroupResource и тесты членства/иерархии. Это общий фундамент обеих веток.
2. **Выбор и хранение правил доступа.** На ревью утвердить A или B, затем добавить только соответствующие таблицы, поля Item, настройки schemes/levels либо visibility/item groups и доменную матрицу.
3. **Authorization perimeter.** Реализовать `ItemAccess`, Policy, SQL scopes, правила участников/групп/руководителей и целостности parent-children-comments-boards.
4. **Filament и REST.** Подключить Access UI и единый perimeter ко всем рабочим поверхностям, обновить API и OpenAPI, проверить попытки обхода через действия и includes.
5. **Миграция и выпуск.** Проверить историческую публичность на копии данных, выполнить полную security-матрицу и регрессию, обновить specs/Roadmap и выпустить только выбранную ветку.

## Итого и рекомендации

Выбрать **Planfix-like** модель для первой реализации: типизированные группы назначаются участниками конкретной задачи, существующие роли Item получают понятные права, а руководители и аудиторы проекта расширяют доступ без сложной настройки схем. Jira-like вариант целесообразен, если обязательным требованием являются переиспользуемые security schemes, несколько уровней и default-политики на проекты; его полноценный проект сохранён в этом RFC. В обоих случаях критичны не access-поля сами по себе, а единый SQL/Policy perimeter для всех UI, связей и REST API.

### Открытые вопросы

- **Выбор ветки перед delivery:** утвердить рекомендованную Planfix-like модель или требование Jira-like schemes. Одновременная поддержка обоих режимов и переключатель в runtime не планируются.
- **Конфиденциальность файлов:** текущие item description и comment attachments используют публичные disk URL. Row-level ACL не защищает файл по известной ссылке; signed URLs/private disk требуют отдельного RFC и не должны считаться закрытыми этой задачей.
- **Противоречие текущей спеки:** [item-comments.md](../specs/item-comments.md) в «Key decisions» называет attachments выключенными, а в «Known limitations» — включёнными. Перед delivery уточнить спецификацию; фактическая защита вложений в любом случае остаётся отдельным вопросом.
- **Скрытые проекты как отдельный раздел:** сейчас проект — типизированная группа без собственного рабочего UI. Отдельные project pages, списки открытых/скрытых проектов и default participants проекта не входят в этот RFC.

### Альтернативные варианты

| Критерий | A — Jira-like | B — Planfix-like (рекомендуется) |
|---|---|---|
| Основная единица настройки | Схема и именованный уровень | Конкретная задача и её участники |
| Групповой доступ | Grant уровня на текущих членов группы | Группа — динамический участник задачи |
| Права операций | Текущие permissive права после view | Ролевая матрица restricted Item |
| Переиспользование политик | Высокое | Через проект/группы, без отдельных схем |
| Сложность администрирования | Выше: schemes, levels, grants, defaults | Ниже: участники, группы, restricted/public |
| Соответствие текущему коду | Требует новой подсистемы | Использует существующие participant relations |
| Основной риск | Ложное ощущение полного Jira RBAC без permission schemes | Изменение прав при переходе public → restricted |
